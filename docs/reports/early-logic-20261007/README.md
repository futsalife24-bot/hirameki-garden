## 比較規則を限定する

**星図の基本規則**は、各星の必要本数と周囲の辺の下限・上限から本数候補を減らすこと、および線が必ず存在すると分かった辺と交差する辺を0本にすることです。たとえば接続先が一つだけの数字2なら、その辺は2本に確定します。確定は「その辺が0本と分かった」場合も含み、描く手数とは違います。

星図の追加規則では、つなげる可能性のある辺全体を見て、ある辺をなくすと星の集まりが分離するなら、その辺を最低1本にします。この追加規則でも第二夜の残りは決まりません。これ以外にも人が使える推論はあるため、「機械が止まった＝人は推理できない／仮置き必須」とは結論しません。

**活字の基本規則**は、語の長さ、既に確定した語との交差、一つの語を複数箇所へ使わないこと、ある語の置き場所が一つだけならそこに確定することです。追加規則は、まだ確定していない交差相手にも、文字が合う候補が少なくとも一つ必要という比較です。候補の順番を逆にしても結果が一致することを確認しました。

どちらも、正解データを推論のヒントにしていません。星図の `sol` と活字の正解位置対応は、推論が終わった後で正解を誤排除していないかを検証するためだけに使います。ただし活字の置き済み語は、ゲームで最初から見える正規の手掛かりとして使います。

## 第二夜の具体的反例

ここで使う星1〜7は `stars` 配列順＋1という資料用の番号で、画面上の数字は必要な線の本数です。座標は左上を(0,0)とします。

| 資料番号 | 座標 | 画面の数字 |
| --- | --- | ---: |
| 星1 | (0,2) | 4 |
| 星2 | (0,0) | 2 |
| 星3 | (2,2) | 3 |
| 星4 | (2,0) | 1 |
| 星5 | (0,4) | 3 |
| 星6 | (4,2) | 2 |
| 星7 | (2,4) | 1 |

基本規則で、星1–5は2本、星3–6は2本、星3–7は0本、星5–7は1本に決まります。残る4辺には各2候補があり、全部で16組。その16組をこの面だけ列挙すると、数字と交差禁止を満たすのは次の2組でした。

| 残る辺 | 数字は合うが不正解の配置 | 正解の配置 |
| --- | ---: | ---: |
| 星1–3 | 0本 | 1本 |
| 星2–4 | 0本 | 1本 |
| 星2–1 | 2本 | 1本 |
| 星4–3 | 1本 | 0本 |

左の配置では **{星1,2,5,7} と {星3,4,6} が分離**します。右だけが全星をつなぐため、正解は一つです。既存生成器の `countSolutions` も第二夜だけ再利用し、解数1を確認しました。今回の新規一意解検算はこの1面に限っています。

人には、星3–6を結んだ後の集まりと星4を見て、「残りの本数がそれぞれ1なので、ここを結ぶと外へ出られない」と推理する方法があります。16組の試行や実際の仮置きが必要だという意味ではありません。**追加した単純な連結規則にも限界がある**という反例でもあり、機械の未確定4辺を人の難度点数に換算しません。

## 改善候補は2案

同じ問題への代替案です。両方の実装を決めたものではありません。

| 候補 | 具体案 | 期待する効果と残るリスク | 採用時の条件 |
| --- | --- | --- | --- |
| A：練習してから第二夜へ | 星図を旧面番号 **[1,3,4,2,5,6,…,30]** の順にする。活字は **[1,2,…,24]** のまま | 正解を追う第一夜の後に、数字から決まる同サイズの2面を置き、孤立を考える旧第二夜へ移る。第三・第四夜の間の優劣は今回判断できないので元の相対順を保つ。旧第二夜が実際に難しいかは未測定 | 順序変更の本人判断に加え、保存の面番号対応を設計する必要あり。今回の資料だけで本番へ適用しない |
| B：順序を保ち、孤立の見方を伝える | 第二夜の該当局面でだけ使える任意の案内文候補：**「数字が合っていても、星が別々の集まりになると完成しません。残り1本どうしを結ぶと、その集まりから外へ出られるでしょうか。」** | 現行順と問題を保ち、今回見つかったルールの切替を直接補助する。正解の辺を名指ししない。現行機能として存在する案内ではなく未実装の候補 | 任意案内の仕様、表示条件、スマホ画面の収まりを別途確認。解答を隠した本人プレイで案内の有用性を確認するまで効果は断定しない |

候補Aの順序案は「少ない盤を易しい順に並べる」という単純な整列ではありません。問題の大きさが同じでも必要な見方が違うという有限の証拠を使っています。5面以降を完全な易→難に整列できた、という主張もしていません。

## 保存と公開の条件

星図の保存は面番号 `level` と星の配列番号を含む辺のキー `b`、ベストも面番号で管理しています。`hoshizu.js` は保存を新しい面の辺集合に合わせて復元するため、単に配列を並べ替えると同じ面番号が別の問題を指し、途中の線やベストが別問題に結び付くリスクがあります。案Aは将来の安定した問題IDや明示的な面番号移行の検討を要し、今回は移行・順序変更を行いません。

活字も面番号と置き場所に対応する `p` 配列、面番号別ベストを保存します。語数が同じだからといって別の面へ安全に順序交換できるわけではありません。今回、活字は推論比較で改善理由が出なかったため変更対象にしません。

新しい案内を実装する場合も本人の仕様判断が必要です。mainはGitHub Pagesの公開元であり、repo AGENTS.mdの公開承認条件を維持します。本評価のcommit/pushはレビュー用ブランチだけです。
